## Register

### D-1 — live-suite per-step budget is smaller than the adapter budget it wraps

- **Lane:** tier-2 LM Studio. L9 ×3 (`test_pipeline_acceptance.py`), L10
  (`test_plan_execute_review.py`), L12 (`test_workflow_run.py`).
- **Symptom:** `StepTimeout: Agent step exceeded the per-step timeout of 30.0
  second(s)`. The HTTP flow returns 504 `step_timeout`.
- **Root cause:** when `MANGOMAS_LOOP__STEP_TIMEOUT_SECONDS` is unset,
  `make_lmstudio_settings` builds `LoopSettings(step_timeout_seconds=30)`
  (`DEFAULT_LOOP_STEP_TIMEOUT`), but the adapter budget it wraps is the
  CPU-sized 240 s (`resolve_live_timeout`). The outer, must-not-fire bound is
  therefore 8× tighter than the inner one. That breaks spec-0029 R2.1 and
  R2.5 ("timeouts that must not fire use the CPU-sized budget"). The suite
  goes green only on hardware fast enough to finish each step in 30 s. The
  2026-10-01 D5 fix added an env escape hatch but pinned the 30 s default
  with a guard, so the defect was codified rather than closed. The
  hardware-contract lint cannot see it, because the value is a named
  constant rather than a numeric literal.
- **Evidence:** the same five tests with only
  `MANGOMAS_LOOP__STEP_TIMEOUT_SECONDS=240` set: 4 pass, and the fifth
  advances to D-2 (`artifacts/validation/lmstudio-h1-step240.txt`).
- **Class:** D-n (test tree: `tests/lmstudio/conftest.py`). Supersedes the
  default-pinning half of the 2026-10-01 D5 guard. Env precedence and explicit
  `loop=` precedence are kept.

### D-2 — `ToolAgent` with no tool registry rejects any fenced JSON reply

- **Lane:** tier-2 LM Studio L10, the shipped `plan-execute-review` graph,
  after D-1 is unblocked.
- **Symptom:** `LLMBadResponse: Tool call JSON is missing the required 'tool'
  key` (502) from the tool hop.
- **Root cause:** `ToolAgent.handle` runs `ToolCallParser.parse` on every
  reply. The parser raises on a fenced JSON block that is not a tool call,
  which is correct when a tool contract was sent to the model. With
  `ctx.tools is None` (the shipped default, RAG off) no tool prompt is sent,
  yet the same strictness applies. In the shipped graph the tool hop routinely
  echoes the planner's JSON plan in a ```` ```json ```` fence, so the
  advertised pipeline fails on a capable model. The parser (protected
  `core/tools.py`) is correct for its contract. The defect is in the agent.
- **Class:** D-n (`src/mangomas/agents/tool_agent.py`). Kept boundaries: a
  configured registry still raises on a botched tool call, and no registry
  with a *valid* tool call still raises `ToolNotFound`
  (`tests/test_tool_agent.py`).
- **Cross-reference:** reported for this SHA in a sibling tree as 2026-10-07
  L-D1 (hypothesis H1). Reproduced here independently.

### D-3 — `tests/test_auth.py` fails `mypy --strict` when `httpx2` is installed

- **Lane:** typecheck in the CUDA population
  (`.[dev,embeddings-local,rag]`).
- **Symptom:** 3 `arg-type` errors at `tests/test_auth.py:328,340,374`:
  `dict[str, bytes]` is not a valid `headers` type.
- **Root cause:** the non-ASCII credential tests pass `{"Authorization":
  b"..."}`. That is a `Mapping[str, bytes]`, which is not a member of httpx's
  `HeaderTypes` (`Mapping[str, str] | Mapping[bytes, bytes] | ...`). Without
  `httpx2`, Starlette types `TestClient` headers as `Any` and mypy is silent.
  `httpx2` arrives through `huggingface_hub`, i.e. the documented
  `embeddings-local` extra, so any developer who installs the GPU extra gets a
  red `make typecheck`. The 2026-10-01 D1 fix cast the *response* type but left
  the header mapping mixed.
- **Class:** D-n (test tree). Fix: send an all-bytes mapping
  (`{b"Authorization": ...}`), which keeps the raw wire bytes the test exists
  to send and is a valid `HeaderTypes` member.
- **Cross-reference:** 2026-10-28 D1 (H1), reproduced.

### D-4 — `RecursionError` from a nested 2xx body escapes the LM Studio adapters

- **Lane:** hermetic probe (`httpx.MockTransport`).
- **Symptom:** `LMStudioClient.complete` and
  `LMStudioEmbeddingClient.embed_batch` raise a bare `RecursionError` on a
  pathologically nested JSON body. The API answers an untyped 500 instead of
  the adapter's typed 502.
- **Root cause:** both parse `resp.json()` inside
  `except (KeyError, IndexError, TypeError, ValueError)`. The C JSON scanner
  raises `RecursionError` (not `ValueError`) past its depth limit. The
  workflow predicate client already catches it
  (`workflow/predicate/_client.py`), so the adapters are the inconsistent
  boundary.
- **Class:** D-n (`src/mangomas/adapters/llm/lmstudio.py`,
  `src/mangomas/adapters/embeddings/lmstudio.py`).
- **Cross-reference:** 2026-10-28 D2a (H1), reproduced.

### D-5 — one malformed SSE chunk aborts the whole stream

- **Lane:** hermetic probe.
- **Symptom:** `_parse_sse_line` raises `AttributeError` for `"delta": null`
  or a string `delta`, and `RecursionError` for a deeply nested chunk. The
  stream dies mid-flight.
- **Root cause:** the function's contract is "None to skip" for unparseable
  chunks, but it calls `.get` on `delta` without checking that it is a
  mapping, and its `except` omits `AttributeError` and `RecursionError`.
- **Class:** D-n (`src/mangomas/adapters/llm/lmstudio.py`).
- **Cross-reference:** 2026-10-28 D2b (H1), reproduced.

### D-6 — an invalid `MANGOMAS_*` value crashes every CLI command with a traceback

- **Lane:** hermetic probe:
  `MANGOMAS_LLM__TEMPERATURE=not-a-float mangomas agents`.
- **Symptom:** a raw pydantic `ValidationError` traceback and exit 1. The
  message echoes `input_value`, so a malformed secret-bearing value would be
  printed to stderr.
- **Root cause:** every command calls `configure_cli_logging`, whose first
  statement is `get_settings()`. Its docstring promises that invalid config
  fails with `EXIT_CONFIG_ERROR`, but `get_settings()` raises pydantic's
  error, not a `MangomasError`, so `build_or_exit`'s mapping never sees it and
  nothing else catches it.
- **Class:** D-n (`src/mangomas/cli/_app.py`).
- **Cross-reference:** 2026-10-28 D3 (H1), reproduced.

### ENV-1 — `[dev]` silently replaces a CUDA torch with PyPI's CPU wheel

- **Lane:** building the CUDA population.
- **Symptom:** `pip install -e ".[dev,embeddings-local,rag]"` over
  `torch==2.11.0+cu128` left `torch 2.15.0+cpu` and
  `torch.cuda.is_available() == False`.
- **Root cause:** the cu128 build requires `setuptools<82`. `[dev]` floors
  `setuptools>=83` (PYSEC-2026-3447), so the resolver swaps in a torch without
  that cap, and on Windows that is the CPU-only wheel.
- **Class:** ENV. Mitigation that resolves cleanly: `torch==2.14.1+cu130`
  (`pip check` clean, both devices visible). The new `make gpu` gate is what
  makes this failure loud instead of silent.

### P-1 — this branch's own GPU port skipped at collection on the `[dev]` population

- **Lane:** `make gate` after the port (caught before any commit).
- **Symptom:** the zero-skip guard failed an otherwise green session:
  `SKIP (collection) tests/rag/test_device_resolution_gpu.py: could not import
  'torch'`.
- **Root cause:** the ported module called `pytest.importorskip("torch")` at
  import time. On the CI population (no torch) that is an unsanctioned skip,
  and with `RUN_GPU=1` it would hide exactly the missing-torch case the gate
  exists to fail.
- **Fix:** count CUDA devices in a helper that returns 0 when torch is
  absent. `torch` / `torch.*` join the optional-SDK `ignore_missing_imports`
  list, next to `sentence_transformers`.
